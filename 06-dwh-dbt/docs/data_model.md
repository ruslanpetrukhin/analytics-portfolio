# Модель данных аналитического хранилища (DWH)

## 1. Подход к моделированию

Для аналитического хранилища выбрана схема типа Star Schema (звезда).

Основная модель включает две фактовые таблицы:

- `fct_order_items` — факты по товарным позициям заказов.
- `fct_order_status_history` — история изменения статусов заказов.

Факты связаны с измерениями клиентов, товаров, дат и статусов.

Основная цель модели — обеспечить корректный анализ продаж, выручки и жизненного цикла заказов.

## 2. Фактовая таблица `fct_order_items`

### Назначение

Хранение информации о товарных позициях заказов для анализа продаж и выручки.

### Зерно таблицы (Grain)

Одна строка соответствует одной товарной позиции внутри заказа.

### Предполагаемая структура

| Поле | Назначение |
|---|---|
| `order_id` | Идентификатор исходного заказа |
| `product_id` | Идентификатор товара в источнике |
| `product_sk` | Суррогатный ключ товара |
| `customer_sk` | Суррогатный ключ версии клиента |
| `date_sk` | Ключ даты заказа |
| `quantity` | Количество товара |
| `unit_price` | Цена единицы товара на момент заказа |
| `revenue` | Выручка товарной позиции |

Для идентификации товарной позиции используется составной ключ `order_id + product_id`, поскольку отдельного `order_item_id` в источнике нет.

### Расчёт выручки

`revenue = quantity × unit_price`

На первом этапе в фактовую таблицу рекомендуется загружать все товарные позиции, включая позиции отменённых заказов. Это позволяет сохранить исходную детализацию.

При расчёте выручки применяется единое бизнес-правило: учитываются только заказы со статусами `paid`, `processing`, `shipped`, `delivered`.

Таким образом, исключение отменённых заказов происходит на уровне бизнес-метрик, а не путём безвозвратного удаления исходных данных.

## 3. Измерение `dim_customers`

### Назначение

Хранение информации о клиентах и истории изменения отслеживаемых атрибутов.

### Предполагаемая структура

| Поле | Назначение |
|---|---|
| `customer_sk` | Суррогатный ключ версии клиента |
| `customer_id` | Идентификатор клиента в источнике |
| `full_name` | Имя клиента |
| `email` | Электронная почта |
| `valid_from` | Начало действия версии |
| `valid_to` | Окончание действия версии |
| `is_current` | Признак текущей версии |

### Историчность

Для атрибутов, изменения которых необходимо сохранять, применяется SCD Type 2.

При изменении отслеживаемого атрибута:

1. Предыдущая версия закрывается.
2. Создаётся новая запись с новым `customer_sk`.
3. Для новой записи устанавливаются актуальные даты действия.

При загрузке факта выбирается версия клиента, действовавшая на дату заказа:

`order_date >= valid_from AND order_date < valid_to`

Это позволяет корректно обрабатывать поздно поступившие факты: версия клиента определяется по дате заказа, а не по дате загрузки данных.

**Ограничение источника:** текущая таблица `customers` не содержит атрибута `segment`. История сегментов может быть реализована только после подключения дополнительного источника, например CRM.

SCD Type 2 для существующих атрибутов `full_name` и `email` является проектным решением, а не уже реализованной функциональностью.

## 4. Измерение `dim_products`

### Назначение

Хранение справочной информации о товарах для анализа ассортимента и продаж.

### Предполагаемая структура

| Поле | Назначение |
|---|---|
| `product_sk` | Суррогатный ключ товара |
| `product_id` | Идентификатор товара в источнике |
| `product_name` | Название товара |
| `is_active` | Признак активности товара |

Источник — таблица `products`.

При необходимости исторического анализа изменений товарных атрибутов можно предусмотреть SCD Type 2.

## 5. Измерение `dim_date`

### Назначение

Календарное измерение для анализа показателей в разрезе времени.

### Предполагаемая структура

| Поле | Назначение |
|---|---|
| `date_sk` | Ключ даты |
| `date` | Календарная дата |
| `day` | День месяца |
| `month` | Номер месяца |
| `month_name` | Название месяца |
| `quarter` | Квартал |
| `year` | Год |

Измерение позволяет строить отчёты по дням, месяцам, кварталам и годам.

## 6. Измерение `dim_order_status`

### Назначение

Единый справочник статусов заказов.

### Предполагаемая структура

| Поле | Назначение |
|---|---|
| `status_sk` | Суррогатный ключ статуса |
| `status_id` | Идентификатор статуса в источнике |
| `status_name` | Название статуса |

Источник — таблица `order_status`.

Справочник используется для унификации статусов в аналитической модели истории заказов.

## 7. Фактовая таблица `fct_order_status_history`

### Назначение

Хранение истории изменения статусов заказов.

### Зерно таблицы

Одна строка соответствует одному периоду действия определённого статуса заказа, представленному в исходной таблице `order_status_history`.

### Предполагаемая структура

| Поле | Назначение |
|---|---|
| `order_id` | Идентификатор заказа |
| `status_sk` | Ключ статуса |
| `status_start_date_sk` | Ключ даты начала действия статуса |
| `status_end_date_sk` | Ключ даты окончания действия статуса |

Таблица позволяет анализировать:

- Количество переходов между статусами.
- Продолжительность нахождения заказа в каждом статусе.
- Время прохождения жизненного цикла заказа.

Для расчёта продолжительности периода могут дополнительно сохраняться исходные временные метки `status_begins` и `status_ends`.

## 8. Связи между фактами и измерениями

Основные связи модели:

**`fct_order_items`:**
- `customer_sk` → `dim_customers.customer_sk`
- `product_sk` → `dim_products.product_sk`
- `date_sk` → `dim_date.date_sk`

**`fct_order_status_history`:**
- `status_sk` → `dim_order_status.status_sk`
- `status_start_date_sk` → `dim_date.date_sk`
- `status_end_date_sk` → `dim_date.date_sk`

`dim_date` используется в нескольких ролях: как дата заказа, дата начала статуса и дата окончания статуса.

Поле `order_id` сохраняется в обеих фактовых таблицах для детализации и сопоставления данных на уровне заказа. При необходимости отдельное измерение заказов можно добавить в дальнейшем.

## 9. Ограничения и дальнейшее развитие

1. Для расчёта прибыли необходимо подключить источник себестоимости или затрат. В текущей базе есть цена продажи, но нет себестоимости.
2. Для историзации клиентских сегментов необходим дополнительный источник, например CRM.
3. Нужно определить единый источник истины для текущего статуса заказа: поле `all_orders.status` или последняя запись `order_status_history`.
4. При загрузке фактов необходимо обеспечить корректное сопоставление суррогатных ключей измерений.
5. Для исторических изменений необходимо определить стратегию обработки поздно поступивших данных.
6. Для SCD Type 2 необходимо обеспечить контроль пересекающихся периодов и наличие только одной текущей версии клиента.

## 10. Статус реализации

**Спроектировано:**
- Зерно фактовой таблицы продаж.
- Структура фактов и измерений.
- Принцип историзации клиентских атрибутов через SCD Type 2.
- Связи между фактами и измерениями.
- Принцип обработки поздно поступающих фактов.

**Не реализовано:**
- Физические таблицы DWH.
- Загрузка данных и формирование суррогатных ключей.
- dbt-модели.
- Автоматизированные тесты.

Модель представляет собой проектную архитектуру аналитического хранилища, основанную на существующей структуре PostgreSQL `FOR CV`.
