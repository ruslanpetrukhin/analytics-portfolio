# Архитектура аналитического хранилища данных (DWH)

## 1. Цель архитектуры

Цель проекта — спроектировать аналитическое хранилище данных на основе существующей операционной базы интернет-магазина PostgreSQL `FOR CV`.

Архитектура должна обеспечить:
- Единые правила расчёта бизнес-метрик.
- Сохранение исторических изменений данных.
- Контроль качества данных.
- Удобную структуру для аналитики и BI-отчётности.
- Возможность масштабирования и инкрементального обновления данных.

В качестве подхода к обработке данных выбран ELT (Extract, Load, Transform).

## 2. Общая схема ELT

Процесс состоит из трёх основных этапов:

1. Extract — извлечение данных из исходной PostgreSQL-базы.
2. Load — загрузка данных в аналитическую платформу без существенных преобразований.
3. Transform — преобразование данных внутри DWH с использованием dbt.

Первоначальная загрузка данных выполняется отдельным инструментом интеграции. dbt используется для последующих SQL-трансформаций, построения моделей и проверки качества данных.

## 3. Слои архитектуры

### 3.1. Raw

Назначение: хранение исходных данных, загруженных из операционной базы.

Предполагаемые таблицы:
- `raw_customers`
- `raw_products`
- `raw_orders`
- `raw_order_items`
- `raw_order_status`
- `raw_order_status_history`

Особенности:
- Структура максимально близка к исходной.
- Бизнес-логика не изменяется.
- Сохраняется информация об источнике и времени загрузки.
- При необходимости поддерживается история поступивших записей.

### 3.2. Staging

Назначение: подготовка исходных данных к дальнейшей обработке.

Предполагаемые dbt-модели:
- `stg_customers`
- `stg_products`
- `stg_orders`
- `stg_order_items`
- `stg_order_status`
- `stg_order_status_history`

Основные операции:
- Приведение типов данных.
- Стандартизация названий полей.
- Обработка некорректных и пустых значений.
- Удаление технических дублей при наличии обоснованного правила.
- Базовые проверки качества данных.

Staging-модели должны сохранять смысл исходных сущностей и не содержать сложной аналитической агрегации.

### 3.3. Intermediate

Назначение: объединение подготовленных данных и реализация повторно используемой бизнес-логики.

Предполагаемые модели:
- `int_valid_order_items` — товарные позиции заказов с применением единого правила учёта статусов.
- `int_customer_history` — подготовка истории клиентов для формирования исторического измерения.
- `int_order_status_history` — подготовка истории изменения статусов заказов.

Основные операции:
- Объединение заказов и товарных позиций.
- Расчёт выручки на уровне товарной позиции.
- Централизация правил исключения отменённых заказов.
- Подготовка исторических данных для SCD Type 2.

### 3.4. Marts

Назначение: формирование аналитических таблиц, готовых для использования в BI и SQL-аналитике.

Предполагаемые модели:

**Фактовые таблицы:**
- `fct_order_items` — продажи на уровне одной товарной позиции заказа.
- `fct_order_status_history` — история событий изменения статусов заказов.

**Измерения:**
- `dim_customers` — клиенты с историей изменений по SCD Type 2.
- `dim_products` — товары.
- `dim_date` — календарь.
- `dim_order_status` — справочник статусов заказов.

Основная фактовая таблица `fct_order_items` имеет зерно: одна строка соответствует одной товарной позиции внутри заказа.

## 4. Контроль качества данных

Для проверки качества данных предполагается использовать встроенные возможности dbt:

- `not_null` — проверка обязательных полей.
- `unique` — проверка уникальности ключей.
- `relationships` — проверка ссылочной целостности.
- Singular tests — проверки бизнес-правил, например отсутствия отменённых заказов в фактовой таблице продаж.

## 5. Обновление данных

Для крупных фактовых таблиц предполагается использовать инкрементальную материализацию dbt.

Основные принципы:
- Загружать новые и изменённые записи.
- Использовать подходящий уникальный ключ.
- Учитывать запоздавшие изменения.
- Предусмотреть механизм повторной обработки данных за прошлые периоды.

Для исторических измерений применяется SCD Type 2 с сохранением периодов действия версий записей.

## 6. Использование данных

Итоговые витрины могут использоваться для:
- Анализа выручки и продаж.
- Анализа товарного ассортимента.
- Анализа клиентских сегментов.
- Анализа жизненного цикла заказов.
- Построения BI-отчётов в Power BI.

## 7. Статус реализации

**Реализовано:**
- Исходная PostgreSQL-база `FOR CV`.
- Структура исходных таблиц и связей.

**Спроектировано:**
- Целевая ELT-архитектура.
- Слои Raw, Staging, Intermediate и Marts.
- Предполагаемые фактовые таблицы и измерения.
- Принципы тестирования и обновления данных.

**Не реализовано:**
- Физическое DWH.
- Загрузка данных в Raw.
- dbt-модели и автоматизированные тесты.
- Автоматизированный pipeline.

Данный документ описывает проектное решение, а не действующую промышленную инфраструктуру.
